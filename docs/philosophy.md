# 设计理念

GIS 系列（gis-kit、gis-view、gis-composer 与本外壳）的共同出发点：**给模型好用的工具和确定的事实，而不是一份规则清单。**

## 1. 为什么不写规则

把领域经验写成 skill 里的“必须/禁止”清单或百科式参考文档，效果往往不好：

- **保守的模型会过度执行**：看到硬规则就停下来反复确认、拒绝继续，或在已有元数据时仍不敢推进；规则越多越互相牵制。
- **规则不了解现场**：文档只能说“注意 NoData”，模型不知道眼前的文件是否真有问题，只能逐一检查或凭空担心。
- **挤占注意力**：几百行注意事项里，与当前任务相关的通常只有一两条。
- **只有地图没有车**：模型知道该注意什么，但每次仍要现写代码，正确性与可复现性没有保证。

## 2. 规则放到哪里

经验仍然重要，只是不以文字形式交给模型，而是落到能自己生效的地方：

| 经验 | 不这样做 | 而这样做 |
|---|---|---|
| CRS 缺失不能猜 | skill 里写“不要从范围推断 CRS” | 引擎发现 CRS 缺失时报错，并给出可执行的修复方式 |
| 注意 NoData、数据类型 | skill 里写“检查 nodata 与 dtype” | hook 读到数据时注入元数据卡片，模型直接看到事实 |
| 分类数据用最近邻重采样 | skill 里列重采样规则 | 引擎根据字段语义选择，或默认值本身正确 |
| 不改源数据 | skill 里写“不要覆盖原文件” | hook 拦截对登记源数据的写入 |

## 3. 原则

1. **给事实，不给命令。** hooks 注入的是“这份数据是什么样”（`describe` 卡片、semantics），由模型自己判断怎么做。事实不会让模型紧张，命令会。
2. **约束在工具里，不在提示里。** 能由引擎检查的就由引擎检查；能由 hook 拦截的就由 hook 拦截。
3. **报错要可操作。** 出错时告诉模型哪里不对、可以怎么改；只在真出问题时出现，比事前警告有效。
4. **skill 只写能力与入口。** 说明有哪些引擎、何时用哪个、如何找到；参数以引擎 `--help` 为准，不复述领域常识。
5. **用评测说话。** 外壳或某条提示是否有用，以 `evals/` 中有无对照的结果为准，而不是凭感觉往 skill 里加内容。

## 4. 与分层的关系

这些原则决定了[分层与边界](boundaries.md)的形状：外壳薄，因为它只提供入口和事实；引擎厚，因为经验固化在引擎代码与报错里；约定只描述事实与声明（见 [contracts/README.md](../contracts/README.md#共同规则)），推测必须显式标注。
